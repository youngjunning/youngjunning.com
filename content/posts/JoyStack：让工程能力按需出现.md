使用 Coding Agent 的门槛不应该是记住一套复杂流程。安装 JoyStack 之后，使用方式仍然是直接描述目标：修一个缺陷、补一项能力、理解一段陌生代码，或者继续一项尚未完成的工作。Agent 根据任务状态选择需要的工程能力，简单改动不会被迫走完整套流程，复杂任务也不会因为一句模糊指令直接跳进实现。

JoyStack 当前由一个统一入口和八个工程模块组成。它不提供新的专有运行时，也不要求使用者逐个点名子模块；真正被固定下来的是模块之间共享的事实、边界与证据契约。

## 安装以后，使用方式不变

安装完整模块集：

```bash
npx skills add youngjunning/joystack
```

随后照常描述任务。例如，“修复上传大文件时偶发失败，并确认不会影响小文件”可能先进入排障：复现失败、缩小条件、定位根因；修复后转入验证，分别检查回归测试、构建和真实上传结果；仓库需要交付时，再核对任务改动、作者身份、目标分支和普通推送是否安全。

这是一个说明路由方式的示例，不代表每项任务都会依次启用三个模块。若只是修正文档中的错字，构建、验证和 Git 交付已经足够；若当前行为尚未查清，Agent 会先理解系统，避免只根据文件名猜一个修改位置。

## 八个模块如何接住一项任务

JoyStack 没有规定固定流水线。每个模块只负责一个可核对的问题，并把结果交给真正需要它的下一环。

| 模块 | 它要回答的问题 | 可交接的结果 |
| --- | --- | --- |
| Understand | 系统现在怎样工作，哪些仍是未知 | 当前行为、来源、影响范围 |
| Shape | 目标、边界和成功条件是否足够明确 | 最小结果、明确不做的范围、验收条件 |
| Build | 怎样用最小切片交付用户可见结果 | 实现改动、局部反馈、残余风险 |
| Verify | 哪些证据足以支持“已经完成” | 已执行检查、覆盖盲点、目标环境待验项 |
| Debug | 异常能否复现，哪个机制导致失败 | 根因、被排除的假设、回归保护 |
| Review | 改动是否满足原目标并保持系统边界 | 可行动问题、触发条件、修正方向 |
| Git Delivery | 任务改动能否安全提交和推送 | 提交、远端回读、保留事项 |
| Continue | 下一轮怎样从已确认状态继续 | 决定、证据、位置、风险和下一步 |

这种拆分避免让一个总控 Skill 同时承担需求澄清、代码实现、测试判断、发布授权和长期记忆。领域 Skill 仍然负责自己的专业判断，例如 UI 设计、数据库迁移或平台发布；JoyStack 只维持跨阶段一致的目标与证据标准。

## 关键是统一交接契约

JoyStack 的核心不在八个名称。每个模块都按同一组信息交接：结果、边界、事实、证据与续接。

这组契约要求分开四类内容：用户已经作出的决定、当前源码或运行状态能够证明的事实、基于证据形成的方案判断，以及仍待验证的事项。旧文档可以帮助定位，却不能替代当前代码；测试通过可以证明受测行为，却不能自动证明已经部署；推送成功也不能冒充真实业务结果。

模块交接还必须保留权限边界。理解代码可以产生修改建议，不能因此获得发布权限；验证发现外部环境缺失时，应说明缺少的账号、设备或输入，更不能把未执行的检查写成成功；续接模块可以压缩已确认状态，不能把整段会话或敏感资料自动写入长期系统。

这些约束让模块可以替换。未来如果出现更好的排障或评审能力，只要它接受相同事实并产出可核对结果，就能补强对应位置，不必把整个工程工作流推倒重来。

## 简单任务为何不会被重流程拖慢

工程流程容易出现两种偏差：每项任务都套同一份检查表，或者为了追求速度省略所有边界。JoyStack 采用按风险升级的策略。

短小、明确、可逆的任务通常只需要确认最小边界，完成改动，执行贴近风险的验证，再按仓库规则交付。只有当任务涉及跨系统状态、数据兼容、权限或付费、外部发布，或者成功条件无法在本地证明时，才额外检查三个问题：这项改变是否仍然解决原问题，失败后怎样恢复，现有证据能支持到哪一层结论。

流程长度由风险决定，项目规模或术语数量都不是判断依据。一个单行配置可能触发生产发布，需要更严格的停止条件；一次涉及多个文件的内部重命名若可逆且验证充分，反而不必先写一份长规格。

## JoyStack 不接管哪些事情

JoyStack 负责工程能力之间的协作。项目事实仍由仓库里的源码、配置、锁文件、测试与当前运行状态解释，项目自己的 `AGENTS.md` 和发布协议也优先于通用模块。

它同样不把 Git 交付等同于产品发布。Git Delivery 只判断本任务文件能否安全提交和普通推送；创建 Release、执行数据库迁移、提交应用商店或变更生产环境，仍需要目标项目的明确规则与授权。

它也不承诺让所有任务自动成功。JoyStack 能做的是让失败停在可解释的位置：事实尚未查清时不急着实现，验收条件不明确时不伪造完成，环境缺失时保留恢复入口。工程 Agent 的可靠性首先来自这些边界，命令数量不能替代它们。

## 从一套公开契约继续演进

JoyStack 已在 [GitHub 公开仓库](https://github.com/youngjunning/joystack/tree/87b4fc75cd4424772ce1f6641590957fb23a05e3) 提供入口、八个模块、目录清单与校验脚本，并采用 MIT 许可。模块的输入、输出和替换规则写在[套件契约](https://github.com/youngjunning/joystack/blob/87b4fc75cd4424772ce1f6641590957fb23a05e3/skills/engineering/joy-stack/references/stack-contract.md)中。

这套设计最终只想保留一个简单的使用界面：描述目标，检查结果。中间选择理解、定形、构建、验证、排障还是评审，取决于任务事实和风险；使用者无须背诵流程。
