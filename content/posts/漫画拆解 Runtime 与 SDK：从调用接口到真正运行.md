我写这篇文章，是因为一句“ChatGPT 用了 OWL”接连引出了三个不同问题：OWL 是给开发者调用的 SDK，还是实际运行网页的 Runtime？Electron 风格的代码能否说明底层一定是原版 Electron？看到扩展管理页面，能否断定 OpenAI 修改了 Chromium？如果把接口、打包物、执行进程和产品界面放在同一层讨论，答案会越说越满，证据却越来越少。

下面的小界和小南走进一间漫画机房。机房、控制器和机器都是**解释用的场景**，不是 ChatGPT 或 Atlas 的真实界面截图。文章中的产品事实以官方文档和本机检查的特定安装包为准；通用概念则用可复用的工程判断方法展开。

![封面：小界与小南打开机器，分辨控制接口和执行引擎](/media/88cddc5b581be236-e9fa2b5670a6200c.webp)

## 一句话总结

**SDK 主要回答“开发者怎样接入和调用”；Runtime 主要回答“程序运行时由什么执行、维持和约束”。两者可以同时存在于一个产品或安装包中，区别取决于职责，不取决于文件后缀、语言、是否开源，或厂商给它取的名字。** API 是双方约定的接口，SDK 常把 API 封装为库和工具；Runtime 则在程序运行期间承载代码、状态、资源和生命周期。调用成功的接口与真正完成工作的执行端，有时在同一进程，有时隔着网络或进程边界。

拿 OWL 来说，OpenAI 对 Atlas 的公开说明同时描述了 OWL Client API 和运行 Chromium 的 OWL Host。只称它为 SDK，会遗漏 Host 及进程隔离；只说“一个浏览器内核”，又会漏掉 Client、通信和应用侧集成。[OpenAI 的 OWL 工程说明](https://openai.com/index/building-chatgpt-atlas/)可以支持这个判断。ChatGPT 桌面版安装包出现 `runtimeName: "owl"`，说明所检查的版本打包了名为 OWL 的运行时；它不自动证明桌面版和 Atlas 的每个进程、每组补丁都相同。

这篇文章给出一条贯穿全文的检查线：**先找调用入口，再找执行主体；再查状态归属、分发边界和失败现场。** 如果五个问题能分别回答，SDK 与 Runtime 就很难混淆。

## 第一幕：遥控器有按钮，机器却没有通电

![第一幕：小界拿到调用接口，小南指出没有启动的执行机器](/media/88cddc5b581be236-32b01db19a119aaa.webp)

小界拿着一块“控制器”，按钮上可以画出打开页面、截图、下载文件。她按下按钮，机房没有动静。小南指向旁边的主机：电源没有接上，浏览器进程也不存在。**一个调用入口写得再漂亮，也不能凭空产生执行能力。**

这个场景故意把两种职责拉开。SDK 可以提供函数、类型、示例、认证封装、重试策略、命令行工具、调试工具，甚至打包一个二进制。但应用能否完成任务，还取决于某个执行主体是否存在：本机进程、浏览器内核、移动设备、远程服务，或者操作系统的能力。SDK 是开发者使用能力的入口，不保证自己就是能力的全部来源。

先看一个最简化的远程服务例子：

```ts
const client = new ExampleClient({ endpoint, token });
const result = await client.renderPage({ url });
```

这里的 `ExampleClient` 是**教学假设**，不是 OWL 或 OpenAI 的真实 API。它可能把请求序列化、签名并发给服务端；真正加载页面的进程在另一台机器。即使 `renderPage()` 返回一张图片，也不能说“图片由 SDK 渲染”。SDK 可能只负责传递请求与解析结果。反过来，一个 SDK 也可能包含本地原生库，在当前进程中直接执行渲染。是否远程，不能由 SDK 三个字推断。

另一个方向同样成立：Runtime 不一定对开发者暴露一套单独命名的 SDK。一个应用可以通过命令行、配置文件、系统调用或网络协议触发它；也可能把 Runtime 私有地封在产品内部。名称是发布方给出的线索，职责要靠执行路径确认。

| 看到的东西 | 它直接说明什么 | 还不能说明什么 |
| --- | --- | --- |
| `import` 一个包 | 代码依赖了某个库或接口 | 该库独自完成所有运行工作 |
| 安装目录里有二进制 | 该版本随包分发可执行组件 | 二进制已经启动或被当前功能使用 |
| 系统里有进程 | 某个执行体正在运行 | 当前请求一定路由到了它 |
| 调用返回成功 | 某条请求路径给出了成功响应 | 业务结果正确、稳定、可恢复 |
| 产品出现设置页 | 应用提供了配置界面 | 配置功能改在内核哪一层 |

这张表是第一次“证据降温”：**界面、接口、安装包、进程、任务结果是五种不同的观察。** 它们可以互相补强，不能相互替代。

## API、SDK、Runtime：三个词各自回答什么

API 是一份交互约定。函数名、参数、返回值、错误码、HTTP 路径、消息格式，都可以属于 API。它描述调用双方能够怎样说话。API 可以写在文档里，也可以通过类型、协议文件或代码表现出来。看到 API，不等于知道谁负责实现，也不等于知道调用发生在同一进程。

SDK 是开发者拿来构建应用的一组材料。核心通常是库与开发工具，可能再附带类型定义、示例、文档、调试工具、代码生成器或本地组件。AWS 将其 SDK 描述为帮助开发者调用云服务的库与工具；[AWS 的说明](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-dg.pdf)也展示了请求签名、重试和错误处理等典型封装。SDK 关注的是**开发时的接入体验**，并不限定它只能是源码包或只能在编译阶段存在。

Runtime 是程序**执行期间**依赖的环境或组件。它可以提供代码执行、模块加载、事件循环、内存管理、垃圾回收、I/O、渲染、进程协调、状态维持等能力；具体包含哪几项，要看产品。Node.js 官方直接称 Node.js 为 JavaScript Runtime，并说明它在浏览器外运行 V8，同时提供 I/O 能力。[Node.js 官方介绍](https://nodejs.org/learn/getting-started/introduction-to-nodejs)是一个比较清楚的例子。

“运行时”还有宽窄两种用法。窄义可能指一个可执行程序及其必要库，例如随应用打包的浏览器宿主。宽义可能包括进程、共享库、配置、系统服务与受控资源。写技术文章时最好把范围说全：是“Node.js 进程”“浏览器 Runtime”“容器运行时”，还是“整个线上运行环境”。把所有在生产环境出现的东西都叫 Runtime，会丢掉分工；把 Runtime 简化成“一个二进制文件”，又会漏掉进程和状态。

可以用一句话检查自己的措辞：**如果把这个组件从运行中的系统移走，功能能否继续执行？** 若答案是不能，它至少承担 Runtime 职责；若组件主要给开发者提供调用、构建或调试入口，它承担 SDK 职责。这个测试不是形式定义，因为一个包可能同时承担两者。它只是帮我们从“包装名称”回到“运行责任”。

### SDK 不是 API 的同义词

一个公开 HTTP API 可以完全不提供官方 SDK；开发者直接发请求照样能用。官方 SDK 往往把相同协议包装成语言习惯一致的函数，处理鉴权、分页、重试和类型。于是 API 是**契约面**，SDK 是**接入包**。有时厂商说“SDK API”，意思是 SDK 对应用开放的函数，并不构成第四种独立层次。

### Runtime 不是操作系统的同义词

Runtime 会依赖操作系统调度线程、分配内存、提供网络和文件接口；操作系统并不因此等同于某个语言 Runtime。Node.js 可以运行在 macOS、Linux、Windows 上，V8 与 Node 的事件循环在自己的进程中工作，而进程仍受操作系统约束。浏览器 Runtime 也如此：网页渲染、JavaScript 执行和网络栈可以随应用打包，窗口、输入、文件与权限仍要与平台协作。

### 一个 SDK 可以自带 Runtime

移动开发套件、游戏引擎、浏览器自动化工具很容易出现“开发包里顺手带着执行端”。开发者安装的是一个 SDK，发布到用户机器上的却可能只保留其中的 Runtime。也可能 SDK 在开发机，而 Runtime 在云端；这时用户机器甚至不会安装 SDK。**打包关系不是职责关系。** 最可靠的说法是：“这个套件包含供开发者接入的 SDK 部分，以及运行时要加载的执行部分。”

## 第二幕：从安装包到响应，一次调用经过五道门

![第二幕：小南启动机器，小界观察安装包与运行状态](/media/88cddc5b581be236-19446c7d9498e380.webp)

漫画里，机器被送进机房只是第一步。小南拆开箱子，连接电源，按下开关，等状态灯亮起，再让小界按控制器。这个顺序对应软件里的**分发、安装、启动、调用、验证**。把其中任意一步当成下一步，都是排障中常见的误判。

第一道门是**开发依赖**。项目声明某个包，编译器能够找到类型，编辑器有补全。此时能确认开发者准备使用它。不能推导生产环境已经携带对应二进制，也不能推导用户机器已经安装依赖。锁文件与源码还要分开看：锁文件说明解析到了某版本，代码才说明哪些入口确实被引用。

第二道门是**交付制品**。打包后要查实际文件：动态库、可执行程序、资源包、配置、架构与签名。源码的 `package.json` 写着 `electron`，与最终 App 包内带了什么 Runtime，不一定一一对应；构建脚本可能替换、裁剪或重打包依赖。讨论“应用内置浏览器”时，安装包比开发仓库里的依赖声明更接近最终用户拿到的东西。

第三道门是**启动与存活**。二进制随包分发，只能证明“可供调用”；运行中的进程、线程或服务才说明相关执行体已经启动。常见的延迟启动、按需加载、单独服务进程会让“安装包里有”与“现在正在用”隔着很长一段距离。进程在列表里出现也还不够，下一道门需要确定当前请求是否真的路由到它。

第四道门是**请求穿透**。应用发起一次操作，要知道接口怎样映射到执行体：直接函数调用、IPC、CDP、HTTP、系统调用，还是消息队列。请求可能被主进程转发，可能被缓存命中，也可能在权限层提前拒绝。这里最能区分 SDK 与 Runtime：前者通常帮助发起、编码或管理请求；后者至少承担某种实际执行或状态维持。双方之间若有隔离边界，协议、超时、重连和版本兼容也会成为真实成本。

第五道门是**结果验证**。HTTP 200、Promise resolve、进程未崩溃，只分别说明它们自己的局部状态。网页是否成功加载，截图是否属于目标标签页，扩展是否真正执行，Agent 的动作是否达成用户目标，都需要对应证据。软件分层解释的终点不该停在“调到了 API”，而要到“这个请求由谁处理，留下了什么可验证结果”。

可以把五道门当作排障顺序，而不是把所有东西一股脑叫“环境问题”：

| 门 | 观察物 | 常见误判 | 下一步应看什么 |
| --- | --- | --- | --- |
| 开发 | 依赖、类型、调用代码 | 能编译就能运行 | 最终制品是否包含所需组件 |
| 分发 | 包、框架、配置 | 带了文件就启用了功能 | 进程、加载记录与启动条件 |
| 启动 | 进程、日志、健康状态 | 进程存在即处理请求 | 路由、Session、请求标识 |
| 调用 | IPC、HTTP、CDP、返回值 | API 成功即任务成功 | 执行端状态与目标对象 |
| 验证 | 页面、文件、业务状态 | 看起来正常即稳定 | 错误路径、重试与版本边界 |

这一模型也解释了为什么一些“SDK 很薄”的系统仍然难以接入：SDK 只是第一道可见门，真正困难的是后面四道门的身份、状态、权限和失败恢复。

### 走一遍“打开网页”，看清每一步的责任

把通用例子落到一次导航请求。应用先根据用户操作拿到 URL 和目标标签页标识；调用侧检查参数，建立请求 ID，并把“导航”交给浏览器宿主。宿主决定使用哪个 Profile 或 Session，创建或复用页面对象，安排网络请求，接收响应，再让渲染进程解析文档并产出画面。最后，宿主把进度、标题、错误或像素变化传回界面，界面才把它显示给用户。这里的“先后”是教学路径，具体浏览器内部会异步并行，也会有缓存、重定向、Service Worker 和已有页面复用。

这条路径里有至少三个不同的“成功”。调用方成功提交请求，是**传输成功**；浏览器收到响应并更新页面，是**执行成功**；用户真正看到目标内容并完成后续操作，才接近**任务成功**。例如请求可能已经到达 Host，但目标网页返回 403；导航事件可能完成，页面却是登录页；页面渲染正常，Agent 仍可能点错同名按钮。把这三种成功压成一个布尔值，会让 SDK 的返回值替 Runtime 承担它不能证明的责任。

再看错误与恢复。若调用方超时，它能否判断 Host 没收到请求，还是 Host 执行后回包丢失？重试会不会重复下载、重复提交表单？如果 Host 重启，旧标签页 ID 是否仍有效？如果页面先完成后又发生重定向，哪个事件是最终状态？这些问题不一定由 SDK 或 Runtime 单独解决，答案常由双方的协议共同定义。SDK 可以封装重试和错误类型；Host 必须保证对象身份、幂等性或清楚告知状态失效。一次普通的 `await navigate(url)`，背后就可能有这组契约。

因此，在设计 API 时，我更关心它能否暴露足够的**可观测状态**，而不只关心方法名是否顺手。至少要能关联请求、标签页与执行会话，区分被拒绝、超时、页面失败和用户取消；若存在自动恢复，还应让调用方知道恢复后原对象是否仍有效。SDK 可以把这些信息整理给开发者，但执行事实要回到 Runtime 或远端服务核实。

## 第三幕：一墙之隔，Client 和 Host 各做什么

![第三幕：小界从隔墙一侧发出请求，小南在另一侧照看执行机器](/media/88cddc5b581be236-1e31b6515b5bb761.webp)

这张图先按通用服务架构理解：小界在左边发请求，小南在右边维护执行机器。墙代表一个**进程边界**，不是“安全一定更好”的装饰。跨过墙以后，函数调用变成消息，局部对象变成需要序列化的标识，崩溃和重启也变成协议设计的问题。

客户端一侧可以提供像 SDK 一样的入口：创建 Session、打开页面、导航、读取状态。Host 一侧可以保存会话数据、创建页面对象、执行渲染、响应输入。若 Host 在另一进程中，Client 的 WebView 对象可能只是远端网页对象的本地句柄。调用代码里的 `webView.navigate(url)` 看上去是一个普通方法，但它可能触发 IPC、权限检查、页面进程分配、网络请求和渲染。**方法名说明意图，不说明所有步骤都发生在当前进程。**

OpenAI 对 Atlas 的描述恰好是一个可核验案例：Atlas 应用是 OWL Client，Chromium 浏览器进程是 OWL Host，两者通过 Chromium 的 Mojo IPC 通信；官方文章列出 Session、Profile、WebView、WebContentRenderer、LayerHost/Client 等客户端抽象，以及下载、扩展、自动填充等服务端能力。[OWL 工程文章的 Client/Host 部分](https://openai.com/index/building-chatgpt-atlas/)支持这些陈述。这里的“Client API”确实有 SDK 式的接入作用，但 OWL 作为完整架构还包含真正运行 Chromium 的 Host。

这也是我把 OWL 在该语境下称为 Runtime 的理由：讨论的是**随产品运行、承载浏览器能力的整体层次**，不只是给开发者发的一套调用库。但这个称呼是按职责做的工程概括，不是声称 OpenAI 把 OWL 正式定义成一个可下载的公开“OWL Runtime SDK”。官方文章公开的是架构与部分接口概念，并没有因此交出完整源码和可复用开发包。

进程隔离还带来一笔双向账。好处是界面与浏览器主进程的卡顿、崩溃可以被更清楚地隔开，Chromium 可以异步启动，应用 UI 可以使用另一套技术栈。代价是需要 IPC 协议、对象身份、输入转发、渲染层合成、断线恢复和版本协调。OpenAI 在 Atlas 文章里解释了这些设计动机，但收益是其产品设计目标与描述，不能拿它直接推算任何其他应用的启动耗时、内存占用或稳定性。

这里还需要区分**进程边界**和**信任边界**。把 Chromium 移到单独进程，能让应用更清楚地管理崩溃和响应性，却不自动保证网页与宿主隔离正确。网页脚本能访问哪些 API、预加载脚本暴露了什么、扩展获得哪些权限、Agent 事件能否触发浏览器级快捷键，都要看各自的权限规则。进程分离提供了可以设置边界的位置，边界是否有效还要看消息设计和实际实现。OpenAI 在 Atlas 工程文章中专门讨论了 Agent 输入绕开特权浏览器层，以及临时会话使用隔离存储的做法；那是 Atlas 的公开方案，不应作为 ChatGPT 桌面版的未核验安全结论。

性能也要按层测量。客户端启动很快，可能只是浏览器 Host 延迟启动；首个网页操作仍可能等待 Chromium 就绪。Host 内存独立计量后，应用主进程的数字可能下降，但系统总内存未必下降。某次导航变快，也可能来自缓存、网络、页面脚本变化，而不是 IPC 架构。要评价这类 Runtime 设计，至少分别记录应用启动、Host 冷启动、首个页面可交互时间、后续页面切换和崩溃恢复。只报一个“打开速度”不足以说明哪一层获益。

升级成本同样是 Runtime 的责任。SDK 可以用语义版本号发布，但它发出的消息格式必须与 Host 理解的版本相容；Chromium 的安全更新还会影响原生补丁、扩展接口和页面行为。如果 Client 与 Host 随一个安装包原子升级，协调相对简单；如果它们单独更新，就需要协商能力、拒绝不兼容版本或保留过渡协议。名字叫“SDK”还是“Runtime”不会消除这些工作，明确所有权才会。

### 为什么 Client API 仍不能被简单叫成“只是遥控器”

漫画的遥控器是为了区分执行责任，真实 Client 往往远比按钮复杂。跨进程渲染时，客户端可能要承接用户输入、坐标转换、图层合成和本地窗口状态；它不一定“零计算”。官方 Atlas 文章就说明了 Swift 客户端需要转译并转发输入事件，把 Chromium 的合成图层接进原生视图。说 Host 承载 Chromium，不意味着 Client 没有运行时代码；说 Client 暴露 API，也不意味着它只是一份类型声明。

所以判断一个组件是否属于 SDK 或 Runtime 时，不必强行选一个词。更准确的问题是：**这一部分供谁调用？运行时做什么？状态保存在哪里？失败时谁重启谁？** 对 OWL 可以分别回答 Client API 与 Host 进程；对其他系统也应尽量按这种粒度描述。

## 用四个熟悉的例子校准词义

### Node.js：叫 Runtime，并不妨碍它提供大量 API

Node.js 负责在浏览器外执行 JavaScript，包含 V8、事件循环和 I/O 等运行能力；开发者同时通过 `fs`、`http`、`process` 等 API 编写程序。若有人因为 Node.js 有 API，就称它“只是 SDK”，显然无法解释 `node server.js` 启动的进程以及代码究竟在哪里执行。反过来，也不宜把 npm 里的每个包都叫“Node Runtime”：多数包只是运行在 Node 环境中的库。[Node.js 官方介绍](https://nodejs.org/learn/getting-started/introduction-to-nodejs)和 [Node API 文档](https://nodejs.org/api/)提供了这两个观察角度。

一个 Node 服务还有至少三层：应用业务代码、Node 运行时、操作系统。若服务调用远程模型，远程服务又是第四层。`npm install` 安装 SDK 包、`node` 运行应用、远程服务执行推理，是三件不同的事。排障时若只盯着 SDK 版本，可能漏掉 Node 版本、平台架构或远程服务状态；若只盯着 Node 进程，又可能漏掉 SDK 的请求参数或重试行为。

### React：库的代码在运行，不代表 React 是浏览器内核

React 官方定位为构建界面的库，Web 页面通常通过 `react-dom/client` 的 `createRoot()` 接入浏览器 DOM。[React 官方文档](https://react.dev/reference/react-dom/client/createRoot)可核对这一调用。React 的代码当然会在页面里执行，Hooks 和协调更新都有运行时行为；但是浏览器解析 HTML、布局绘制、处理网络与 DOM 环境，并非 React 单独提供。把“这个产品使用 React”直接推成“网页由 React Runtime 而不是浏览器执行”，混淆了库内的运行时代码和承载它的浏览器环境。

“Runtime”并不是只能属于最底层。React 自身也可有运行时实现；只要明确是在讲 React 的组件执行和更新逻辑，叫 React Runtime 有语境。问题出在用同一个词跨过层次：讨论浏览器内核时，React 不是 Chromium 的替代品；讨论组件协调时，浏览器内核又不是 React 的替代品。

### Electron：Framework、API 与打包的执行层同时存在

Electron 官方介绍它结合 Chromium 与 Node.js 来构建桌面应用。[Electron 文档](https://www.electronjs.org/docs/latest/)同时有 BrowserWindow、WebContents 等应用 API，也有承载网页与 Node 能力的运行组件。Electron 通常作为桌面应用框架被讨论，因为它给出了窗口、进程、IPC 和网页视图的整体开发模型。说它是 Framework，并不排斥它在最终应用里承担 Runtime 职责；“框架”回答怎样组织应用，“运行时”回答应用启动后由谁执行。

如果你第一次接触 Electron，先把三个名字拆开。`BrowserWindow` 是桌面上可见的应用窗口，像相框；`WebContents` 是 Electron 在**主进程**里用于加载、控制和监听一份网页内容的对象，像相框后面的页面控制台；渲染进程则负责真正执行页面代码并绘制网页。`WebContents` 不是网页里的 DOM，也不是 Chromium 内核的另一个名字。一个 `BrowserWindow` 有自己的 `win.webContents`，主进程可以用它加载 URL、观察导航事件、向页面发消息。具体 API 见 [Electron 的 webContents 文档](https://www.electronjs.org/docs/latest/api/web-contents)。

`<webview>` 又是另一层：它是**在应用自己的网页界面中嵌入另一份网页**的标签。可以把它想成在应用窗口的页面里开了一块独立的“网页屏幕”；被嵌入的网页叫 guest，它也有自己的 WebContents，和承载应用界面的 WebContents 不是同一个对象。于是，在截图里看见一个网页嵌在 ChatGPT 窗口中，并不意味着它直接就是整个窗口的 `win.webContents`。当文章说“为 guest WebContents 配置安全选项”，说的是给这块嵌入网页的执行环境设置规则，而不是给 HTML 标签换样式。[Electron 的 `<webview>` 文档](https://www.electronjs.org/docs/latest/api/webview-tag)和 [BrowserWindow 文档](https://www.electronjs.org/docs/latest/api/browser-window)可对照阅读。

用一条最小关系线记忆即可：**桌面窗口 `BrowserWindow` → 应用界面的 `WebContents` → 界面里的 `<webview>` → 被嵌入网页的 guest WebContents**。这不是说每个 Electron 应用都必须使用 `<webview>`，也不是严格的进程树；它只帮助我们辨认这张截图里谁承载谁、谁控制谁。理解这四层以后，再讨论“安全配置是写给哪个 WebContents 的”，就不会把窗口、标签和网页执行环境混成一团。

```text
BrowserWindow                  桌面窗口
└── WebContents A              应用自己的网页界面
    └── <webview>              界面中的嵌入位置
        └── guest WebContents B 被嵌入的目标网页
```

这张小图只画界面承载关系。`A` 和 `B` 是两份不同的网页内容；不要据此推断它们必然对应两个固定进程，或断定所有浏览器功能都要从 `<webview>` 标签直接实现。

Electron 允许为上游依赖维护补丁，官方明确介绍了 Chromium、Node.js 等依赖的补丁目录与维护理由。[Electron 补丁指南](https://www.electronjs.org/docs/latest/development/patches)证明**技术栈允许修改上游**，但它不证明某个具体应用打过补丁，更不证明补丁改了哪个功能。软件可以在 Electron API 之上做大量应用逻辑，也可以维护自己的原生层；只有实际源码、补丁、构建记录或其他强证据才能把变化定位到内核。

### OWL：同名组件可以同时具有 SDK 面和 Runtime 面

OWL 是 OpenAI’s Web Layer。OpenAI 公开描述的 Atlas 版本，有供应用调用的 Client 库和实际运行 Chromium 的 Host。若工程师问“怎样调用 OWL”，讨论重点落在接口；若问“网页由谁执行”，讨论重点落在 Host；若问“如何让浏览器不拖慢原生界面”，则要看进程隔离、异步启动和渲染交换。[官方架构文章](https://openai.com/index/building-chatgpt-atlas/)正好跨过这些问题。

在我检查的 **ChatGPT 26.1023.51421 macOS 安装包**里，`owl-electron-app.json` 的 `runtimeName` 是 `owl`，应用代码仍使用 Electron 风格的 `<webview>`、`WebContents` 和浏览器管理接口。这说明该版本不是简单依靠系统 `WKWebView` 呈现网页，也不能把所有能力归结为“装了原版 Electron”。但安装包字段和静态代码仍不足以证明 ChatGPT 桌面版完全复用了 Atlas 的 Swift Client/Host 结构，或给出准确的 Chromium 补丁清单。具体检查过程见[《漫画拆解 ChatGPT App：内置浏览器藏在哪里》](./漫画拆解%20ChatGPT%20App：内置浏览器藏在哪里.md)。

Atlas 与 ChatGPT 桌面内置浏览器还是两个产品。OpenAI 的 [Atlas 产品公告](https://openai.com/index/introducing-chatgpt-atlas/)现明确标注 Atlas 已弃用；[ChatGPT 桌面内置浏览器说明](https://help.openai.com/en/articles/20001277-using-the-built-in-browser-in-the-chatgpt-desktop-app)则描述当前桌面客户端内的浏览体验。把 Atlas 的架构文章作为理解 OWL 的依据是合理的，把 Atlas 的每个实现细节直接写成 ChatGPT 桌面版的确定事实则超出证据。

### 同一个安装包，开发包和执行包怎样分开

把一套系统交给开发者和最终用户时，SDK 与 Runtime 的内容可能重叠，也可能完全不同。开发包往往带类型、头文件、模拟器、调试符号和示例；用户安装包通常只保留应用运行必需的库、服务和资源。不能因为开发仓库里有某个依赖，就认定最终用户也带着完整 SDK；也不能因为最终包里有大量库，就说它们全部面向第三方开发者开放。

以浏览器自动化工具为例，开发者可能通过 JavaScript 包调用 `launch()`，本地另有浏览器可执行文件或远程浏览器服务。这个包在使用体验上像 SDK；浏览器进程是 Runtime；如果包负责下载并启动浏览器，它还承担**管理 Runtime 的职责**。换成另一种分发方式，浏览器预装在系统里，SDK 就不再“自带 Runtime”。同一 API 形状，交付责任却不同。排障与版本升级必须按实际分发方式重新判断。

再以插件系统为例，开发者拿到插件 SDK，按接口实现一个扩展；应用内的插件宿主负责加载、隔离、调度和卸载。SDK 可以定义钩子，宿主能否在恰当时机调用它才是 Runtime 行为。安装插件成功只是分发状态，启用插件是配置状态，扩展代码执行是运行状态，最终对页面产生效果是业务状态。把它们拆开，刚好能解释为什么“扩展管理页长得完整”仍不足以证明底层哪一行 Chromium 代码被修改。

还有一个反方向的例子：游戏引擎常同时提供编辑器、项目模板、脚本 API 和发布后运行的引擎组件。开发时称它“引擎 SDK”说得通；分析玩家设备上的崩溃时，只说 SDK 就会掩盖实际执行代码、图形驱动和资源加载路径。**术语应随问题切换观察面，不要求产品只能领一个名牌。**

## 第四幕：扩展管理页面能说明哪一层

![第四幕：小界和小南逐一检查包装、接口和正在运行的机器](/media/88cddc5b581be236-4c88cfb262ae5c46.webp)

讨论 ChatGPT 内置浏览器时，还看到“设置 → 浏览器 → 扩展程序”页面：有搜索、开发者模式开关、应用商店入口，也能管理已安装扩展。这个截图是**截图所示客户端版本提供扩展管理界面**的观察。它比一篇泛泛的功能介绍更接近产品表面，却仍然只在界面层建立证据。

扩展能工作，至少要有管理 UI、扩展包处理、权限策略、浏览器扩展能力、页面注入或对应执行机制等环节。界面由应用自己绘制，扩展执行可能调用已有 Chromium 机制，也可能经过 OWL 的服务端接口和应用的权限管理。OpenAI 的 Atlas OWL 文章明确提到扩展服务端入口；ChatGPT 桌面版官方说明也把扩展列为内置浏览器能力。但这两条官方材料，加上一个设置页截图，仍不足以画出 ChatGPT 当前版本的完整扩展调用链。更不能由“看起来像 Chrome 扩展页面”断言“内核被打了某一类补丁”。

要把“有扩展管理 UI”推进到“某扩展真正可用”，至少需要安装一个可核验的扩展，观察其权限、注入、更新和卸载行为，并限定客户端版本与账号状态。要再推进到“该能力由 Chromium 补丁实现”，需要补丁源码、构建配置、符号、运行追踪等能排除纯应用层实现的证据。**功能存在、执行成功、实现层位置，是三个不同结论。**

同理，Electron `<webview>` 的安全设置也应放回正确位置。`sandbox: true`、`nodeIntegration: false`、`contextIsolation: true`、`webSecurity: true` 这组字段若出现在主进程为 guest WebContents 设置的 `webPreferences` 中，说明应用配置了页面隔离选项；不能把它写成 `<webview>` 标签自身的全部配置，也不能凭几个布尔值宣布安全审计完成。[Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)解释了 `will-attach-webview` 等控制点。

## 为什么“看到了运行时”仍不等于“知道内核改了什么”

检查安装包是必要步骤，尤其当源码不开时。包内 Framework 名称、版本、配置、依赖、字符串、导出符号、进程行为，都能提供线索。但这些线索的证明力不同。`runtimeName: owl` 说明打包器把当前执行层标为 OWL；它不是补丁列表。某个方法名含 `owl`，说明应用或运行时暴露了对应接口；它不自动说明接口在 Chromium 源码的哪一个文件实现。

真正要回答“是否定制 Chromium”，有三种强度逐渐增加的材料。第一是厂商公开陈述；OpenAI 对 Atlas 文章明确写到希望维持**定向、较小的 Chromium 补丁集**，足以证明 Atlas 的 OWL 设计涉及 Chromium 上游补丁。第二是源码或构建记录，能定位 patch、commit 和版本基线。第三是可重复的二进制或运行行为对照，能够确认某项具体能力确实不同于上游，并尽可能排除配置和应用层实现。三者可以互补，不能把第一种自动升级成第二种的完整细节。

对 ChatGPT 桌面版，当前已检查到 OWL 打包标识和 Electron 风格应用代码；OpenAI 的 OWL 工程说明则针对 Atlas。因此可以说“该安装包使用名为 OWL 的运行时”，也可以说“OpenAI 公开承认 Atlas OWL 维护 Chromium 补丁”；**不能据此列出 ChatGPT 26.1023.51421 的补丁清单，或断言它与 Atlas 二进制完全相同。** 这不是故意保守，而是把两个不同证据作用于它们各自能够覆盖的对象。

“OWL 开源了吗”也要沿同样方法回答。截止本文核验时，OpenAI 公开了 [OWL 架构文章](https://openai.com/index/building-chatgpt-atlas/)，其中提到 OWL 在内部作为预编译二进制交付；我没有找到 OpenAI 官方提供的 OWL 源码仓库、源码许可证或面向外部开发者的可安装 SDK。因此目前**不能把 OWL 称为已开源项目**。这句话描述的是本次可核验的公开状态，不是证明世界上不存在任何代码片段。网上其他同名 OWL 项目也不能因为名字相同，就当成 OpenAI 的 Web Layer。

## 工程师给组件贴标签之前，先做这张检查表

面对陌生组件，不妨先把“它是什么”暂时改写成五个问题。第一，**谁调用它**？应用代码、开发者工具、浏览器页面、Agent，还是另一个服务？第二，**谁执行工作**？当前进程、子进程、系统服务、远端 API，还是某块硬件？第三，**谁保存状态**？Cookie、Session、文件、内存、浏览器 Profile、任务进度分别属于谁？第四，**随什么分发**？开发依赖、最终安装包、云端部署、操作系统预装，需要分开。第五，**失败由谁处理**？调用方重试、Host 重启、应用恢复，还是用户手动接管？

把答案填在同一行，比争论“这到底算不算 SDK”更有效：

| 对象 | 调用入口 | 执行主体 | 状态归属 | 恰当的描述 |
| --- | --- | --- | --- | --- |
| 远程服务的语言包 | 应用导入的函数 | 远端服务 | 多在远端，部分在本地 | 服务 SDK；远端另有 Runtime |
| Node.js | `node` 命令与内置 API | Node 进程、V8 等 | 进程及应用自己管理 | JavaScript Runtime，附带 API |
| React Web 应用 | React 组件与 React DOM API | 浏览器中的 JS 与 DOM 环境 | 组件状态、浏览器状态分开 | UI 库运行在浏览器环境中 |
| Electron 桌面应用 | Electron API | 应用进程与随包分发的 Chromium/Node 能力 | 应用、Session、系统分别管理 | 框架与运行时共同组成应用 |
| Atlas 中的 OWL | OWL Client API | OWL Host 中的 Chromium | Profile、Session 与应用状态分层 | Client 接口加浏览器运行层 |

表格最后一行**仅指 OpenAI 公开的 Atlas 架构**。给 ChatGPT 桌面版填写同样完整的一行，仍需要该版本更直接的进程和实现证据。表格不是产品排行榜；它说明同一个词在不同边界下如何落位。

还有三个容易造成误会的命名习惯。其一，“Runtime”常被当成“生产依赖”的泛称，结果连配置文件和远程服务都被塞进一层；最好补上“语言执行”“浏览器进程”或“插件宿主”等限定。其二，“SDK”常被当成“所有开发者能碰到的东西”，结果 CLI、编译器、Runtime 都失去自己的位置；最好说清包内各部分的职责。其三，产品可能使用自定义品牌名，例如 OWL；品牌名描述所有权与项目边界，不替代系统调用链的说明。

### 三个反例：别让术语替证据做决定

第一个反例是**纯网络 SDK**。它可能只有几十个封装方法，内部通过 HTTPS 访问云服务。这个 SDK 自己运行在应用进程中，但它不是云端模型的推理 Runtime。若模型响应慢，要同时排查本地序列化、网络、服务排队和模型计算；“SDK 慢”只是症状，未说明瓶颈。若调用失败，也要看身份认证和服务错误是否被 SDK 改写。能在应用中执行的库，不一定是任务主体。

第二个反例是**可嵌入库**。一个图片解码库可以随应用打包，在当前进程执行主要计算，没有额外服务进程。它可能同时是开发者调用的 SDK 部分和实际干活的运行时代码。此时硬要画一堵“SDK 左边、Runtime 右边”的墙反而误导。更准确的图是一层库内部同时包含公开 API 与解码实现，操作系统提供线程和内存，应用管理输入输出。只有在真实存在进程或权限边界时才画墙。

第三个反例是**只在构建时运行的工具**。代码生成器读取 schema，输出客户端源码；构建完成后生成器不随应用分发。它是开发工具，可能属于 SDK，但不是用户运行应用时的 Runtime。生成的代码可能进入运行路径，也可能继续调用别的服务。只看项目仓库中的可执行脚本，会误把构建阶段的组件写进生产执行链。检查最终制品和进程，是排除这种误判的最快办法。

这些反例的共同作用，是防止一条过于顺口的公式变成教条。SDK 不总是远端服务的薄壳，Runtime 不总是独立进程，API 也不总是网络协议。**先描述实际调用和执行，再选择能够压缩事实的术语。**

### 四种排障场景会怎样改变提问

**代码能编译，点击却没有反应**。先别说“SDK 已经验证过”。类型检查通常只证明调用形状与本地声明相容，无法证明宿主进程已经启动、页面对象仍有效、权限已授予，或事件能回到界面。先记录调用请求 ID、目标对象 ID 和宿主接收日志；如果请求根本没有到达宿主，再查桥接与序列化；如果到了宿主但没执行，再查状态机与权限。这样把一个模糊的“按钮坏了”拆成可定位的边界。

**安装包里找到了 Chromium，却打不开任意网页**。二进制存在只证明打包事实。还要确认该平台架构能加载它、启动参数与资源路径正确、宿主没有在启动时崩溃，以及产品是否有意限制可访问的地址或只允许特定入口。发现 Chromium 文件，最多支持“分发了浏览器相关组件”；不能据此写成“开放了通用浏览器 API”。若某个版本工作、另一个版本失效，还应比较签名、权限声明和配置变化，不要先猜源码补丁。

**扩展管理页能打开，扩展却无法影响页面**。页面只证明产品提供了管理入口。继续检查扩展是否真的安装、启用，是否符合当前 Manifest 能力，目标页面是否落在授权范围，内容脚本是否注入到正确的页面和 Frame，消息是否抵达后台上下文。即便确认扩展执行，也不能直接推出它依赖的是原生 Chromium 扩展机制、封装后的兼容层，还是产品自己的脚本注入通道；必须找到能区分三者的证据。

**Agent 说完成了操作，页面状态却没变**。这时要对齐至少四个时间点：Agent 发出动作、Host 接受动作、页面产生事件、任务目标出现。动作可能打到旧标签页、遮挡元素或跨域 Frame；宿主可能把输入发给了页面，但页面随后刷新；模型也可能把“已点击”误当“任务完成”。SDK 的成功回包证明不了最终业务状态，Runtime 的导航成功也证明不了表单提交。把最后一步交给页面状态或后端结果验证，才算闭环。

这四种场景的重点不是背诵“SDK 管调用，Runtime 管执行”，而是每次都问：**哪个组件拥有当前事实，哪条记录能证明它，下一条记录在哪里**？这样命名才会推动调查，而不是把问题提前回答掉。

## 要不要用“Runtime”这个词：我的判断框架

遇到文档命名、架构评审或源码调查，我会先画最短的一条请求路径：**开发者/应用 → 调用入口 → 执行主体 → 可验证结果**。如果只需要说明开发者如何集成，写 SDK 并指出它调用什么；如果要说明执行环境、进程、资源和状态，写 Runtime 并指出它暴露什么接口。如果一个产品两头都做，就分两句描述。争论一个词能否“包住一切”，通常不如把边界写清楚。

对三类读者，结论不同。正在**接入服务**的人，重点关注 SDK 的 API、版本、重试、鉴权与错误语义，同时确认远端或本地 Runtime 谁维护。正在**排查桌面应用**的人，重点关注最终安装包、进程、Session、页面宿主、IPC 与实际行为，不能只从 package.json 认定运行时。正在**评估自研浏览器**的人，重点关注 Chromium 版本、补丁维护、权限隔离、扩展兼容和升级成本，不能只凭一个可见菜单推断内核工作量。

OWL 是一个很好的结尾案例：Atlas 的公开资料足以解释“为什么这不只是 SDK”，本机 ChatGPT 安装包足以把 OWL 标识定位到一个具体版本；两者加起来仍不足以还原 ChatGPT 桌面版的全部内部实现。工程判断最有用的地方，常常是知道**哪一步已经有证据，下一步还需要什么证据**。
