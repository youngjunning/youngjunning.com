在接入 Jev 图像能力时，我要让手机 Agent 根据当前截图找到“查询”按钮，再决定能否点击。Jev 的 `Box` 可以给出位置，但目标可能根本不在屏幕上，截图也可能在点击前过期。沿着 Jev 的一次定位请求往下看，`Noul`、`Box`、目标边界框与视觉 Grounding 分别承担什么角色，以及为什么拿到框还不能直接点击，就清楚了。

## 一句话总结

**Jev 用 `Noul` 判断截图中是否有目标，用 `Box` 获取目标边界框；这两类问题共同服务于按描述在图像中找位置的视觉 Grounding。** 边界框只给出区域，动作系统还要换算坐标、检查截图是否仍然有效，并验证点击后的页面变化。

## Noul 和 Box：同次提问，先判断能否采纳位置

**一句话定义：视觉 Grounding 是根据图像和目标描述，找出描述所指对象在图中的位置。** 对，Jev 的 `Box` 可以看作视觉 Grounding 的一种具体接口实现：它用 bounding box（矩形边界框）表示目标区域，因此叫 `Box`；返回值包含 `left`、`top`、`right`、`bottom` 四条边及这个位置答案的 `confidence`。

`Noul` 和 `Box` 是 Jev 的两种**问题类型**，不是两个先后运行的模型。给它们同一张截图和同一个目标描述：`Noul` 回答“图中有没有查询按钮？”，返回 0 到 1 的“是”的概率；`Box` 回答“查询按钮在哪里？”。`Noul` 的数值不是位置，也不是 `Box` 的置信度。

两种问题可以放在同一次请求中，由 Jev 针对同一张图分别作答。动作系统读取结果时，先判断 `Noul` 是否足以支持“目标存在”，再决定能否使用 `Box` 给出的区域；这描述的是**采纳结果的顺序**，不要求先调用 Noul、再调用 Box。因为 `Box` 即使找不到目标也会返回一个框，只有框而没有存在性判断，可能误点别处。[TypeSafe 的 Noul 文档](https://docs.typesafe.ai/primitives/noul)说明了是/否概率的含义；[Box 文档](https://docs.typesafe.ai/primitives/box)给出了两种问题同次请求的示例。

同次提问省去等待 `Noul` 返回后再发第二次请求的往返，但文档没有承诺服务端并行执行两类问题。若目标经常缺失，先问 `Noul` 再按需问 `Box` 也可能减少不必要的位置计算；实际延迟和成本要按业务截图测量。

## 从截图到点击的流程

同一张截图进入 Jev 后，`Noul` 和 `Box` 分别回答“有没有”和“在哪里”。`Noul` 的结果决定是否采纳 `Box`；目标不存在或证据不足时停止点击。目标存在时，动作系统再换算边界框、复核截图状态，最后点击并观察页面变化。下文按同次请求、结果采纳与坐标换算三个阶段展开。



`Box` 是 Jev 回答目标位置问题的接口，边界框是它给出的矩形数据。`Noul` 为这个流程补充存在性证据，避免把“无论如何都会返回的框”直接当作可点击目标。

“目标边界框”是通用的数据结构。目标检测、OCR、无障碍节点和视觉 Grounding 都可能给出框；**有框不等于用了视觉 Grounding**。区别在于位置如何得到：视觉 Grounding 依据图像和目标描述寻找对应区域；无障碍树的 bounds 来自应用暴露的控件信息。

Jev 1.14 的 `Box` 则是视觉 Grounding 的一个具体接口。请求中放入图片，再用一句话描述要找的对象，例如“截图中的查询按钮”。模型返回图像中该对象的矩形位置。[TypeSafe 的 Box 文档](https://docs.typesafe.ai/primitives/box)把四条边定义为相对于图像宽高的比例，取值范围是 0 到 1。

## Box 给出边界框，点击坐标由动作系统计算

下面的两步是**接入 Jev 的工程代码**负责的，不是 `Box` 已处理好的结果。`Box` 只返回相对输入图片宽高的四条边和位置答案的 `confidence`；它不返回截图像素坐标、设备点击坐标，也不负责判断点击后页面是否按预期变化。

假设截图是 400×400 像素，目标边界框为：

```json
{
  "left": 0.20,
  "top": 0.40,
  "right": 0.80,
  "bottom": 0.60
}
```

**第一步：换算图像像素。** 动作系统用截图的宽高乘以四条边，得到像素区域 `(80, 160)` 到 `(320, 240)`。如果目标适合点击中心，图像中的候选点击点是 `(200, 200)`；下面的代码是工程侧的计算示意，不是 Jev `Box` 的返回值：

```ts
const x = Math.round(((box.left + box.right) / 2) * imageWidth);
const y = Math.round(((box.top + box.bottom) / 2) * imageHeight);
```

![一张 400×400 图中，目标矩形、模型返回的边界框及中心点的位置关系](/media/e196ba9ba7b3b8ed-77e872d332472174.svg)

**第二步：映射到设备并复核画面。** `(200, 200)` 仍是图像坐标。实际设备可能存在截图缩放、裁剪、旋转、状态栏或内容视口偏移。动作系统必须按**执行点击时所用坐标系**重新映射，不能把缩略图上的像素直接交给手机；点击前还应确认截图没有被新页面取代。点击后的页面变化另行验证。

## Box 找不到目标时也会给框

这是最容易误用的地方。按 [TypeSafe 文档](https://docs.typesafe.ai/primitives/box)，`Box` 没有“未找到”结果：即使目标不在图中，它仍返回一个框。仅用 `confidence` 或“框的中心落在屏幕内”就执行点击，会把不存在的目标当成真实控件。

同一次请求可以再问一个 `Noul`：“目标是否出现在截图中？”`Noul` 返回 0 到 1 的肯定概率；当存在性证据不足时，动作系统应停止使用该 Box，重新观察或转用其他证据。TypeSafe 官方也建议[用 Noul 配合 Box](https://docs.typesafe.ai/primitives/box)。阈值需要根据目标和误点代价评测，不能从单次样例推导。

一次安全的定位到动作流程可以写成：

```text
采集当前截图 → 同次提问 Noul（是否存在）与 Box（目标位置）
→ 检查 Noul；证据不足时丢弃 Box 并停止
→ 证据足够时校验 Box 与截图版本，换算设备坐标
→ 点击 → 重新观察并验证页面效果
```

最后一步尤其重要：坐标命中不证明业务动作成功。弹窗遮挡、页面滑动、点击区域过小，都可能让动作落在预期之外。

## 一次最小探针证明了什么

我用 400×400 的白底合成图测试：黑色矩形实际位于 `(80, 160)` 到 `(320, 240)`，规范化边界为 `0.20/0.40/0.80/0.60`。Jev 1.14 对“黑色矩形是否存在”的 `Noul` 给出 `0.99`；`Box` 返回 `left=0.21`、`top=0.37`、`right=0.78`、`bottom=0.64`，置信度 `0.94`。框覆盖了目标中心。

这次结果说明该请求链路能接收图片，并在这个简单样例上给出可用的位置。它没有证明复杂手机页面的定位准确率，也没有证明端到端点击成功。尤其在密集列表、重复按钮和文字很小的页面，目标描述必须足够具体，必要时先裁剪或放大区域。[图像请求格式](https://docs.typesafe.ai/images)与 Box 当前仍被 TypeSafe 标为实验能力；上线前应按实际页面测缺失目标、重复目标、遮挡和延迟。

## 它和页面理解、Accessibility Tree 怎样配合

页面理解需要回答“现在是表单还是结果页”“哪个字段属于当前任务”“点击后是否完成”。视觉 Grounding 只回答其中一个更窄的问题：**指定目标在当前图像中的位置**。一个 Box 无法替代整页结构化观察，也不能判断业务结果是否正确。

Accessibility Tree 能提供控件文本、角色、状态和 bounds；信息完整时，它通常给出更直接的操作目标。缺少标签、绘制在画布里的元素或视觉上可见但未暴露节点的控件，才需要截图定位补足。无论位置来自无障碍树还是 Box，最终都应绑定当前画面，并在动作后核验效果。

## 要不要用 / 我的判断框架

- **值得上**：目标在截图中清晰可见，但没有稳定的无障碍节点；系统具备存在性判断、坐标映射和动作后验证。
- **可以再等**：无障碍节点已经稳定暴露目标与边界，额外的图片请求只增加延迟；或当前无法保证截图与点击使用同一画面状态。
- **重点关注**：目标缺失时的误框、多个相似目标、缩放与视口偏移、截图过期，以及真实页面上的成功率和耗时。单次 Box 命中只能算定位探针通过。

我会把 Box 作为“按描述找区域”的能力来评估，把目标边界框当作待验证的坐标证据。只有存在性、坐标系和点击后的效果都闭合，视觉 Grounding 才真正参与了可靠的自动化。
